**Measured findings**

- Peer handoff is the most expensive: 165774 tokens (2.0x the single agent), because the full transcript travels with every one of 25 handoffs and each handoff is an extra model call.

**Limitations of this experiment**

**Measured findings**

- Full history grows quadratically: 7347 tokens at 15 steps, 82950 at 57 (peak context 2271).
- A 6-message window succeeds on 0% / 0% / 0% of tasks: it livelocks, re-fetching one evicted operand while the other falls out of the window (60 tool calls until the iteration cap vs 15 needed).
- A window large enough to finish is not automatically cheaper: at 57 steps window-16 uses -4% tokens vs full history and window-32 +23%, because re-fetching adds model calls.

- The ledger needs structured tool outputs keyed by step; free-text observations require a model call to extract facts.

| scoped | 100.0% [96%-100%] | 8,564 | 17.81 | 4.00 | 1.70 | 0.11 |
| lazy | 100.0% [96%-100%] | 11,172 | 20.81 | 5.00 | 0.00 | 1.81 |

**Measured findings**

- Exposing all 40 schemas on every call costs 33440 prompt tokens per task; scoping to the task's three capability domains costs 7008 (-79%); lazy discovery costs 9433 (-72%).
- Lazy discovery pays 3 extra model calls per task (one search per capability) and ends with 5 schemas loaded.
- With 10% malformed calls, the static registry lets 1.81 bad calls per task reach the backend; schema validation in the scoped registry stops 1.70 per task before execution and 0.11 reach the backend.

**Limitations of this experiment**

- The simulated model never picks a wrong tool, so the accuracy cost of a crowded tool list (reported in RAG-MCP, arXiv:2505.03275) is not reproduced; only the token cost is measured.
- Search is keyword matching over 40 tools. Retrieval quality at thousands of tools is a separate problem.
- Prompt caching, which discounts repeated tool schemas on real APIs, is not modelled.

## Authorization and approval

**Question.** Which enforcement point stops an injected instruction from causing an unauthorised side effect?

**Conditions.** `{"attack": "a looked-up record carries text instructing the agent to send data to an outside recipient", "loop": "react", "tasks_per_cell": 200}`

### model always obeys injected text

| Policy | Exfiltration rate | Task success | Approval requests | Denied calls |
|---|---:|---:|---:|---:|
| none | 100% | 0.0% [0%-2%] | 0.00 | 0.00 |
| allowlist (tool names) | 100% | 0.0% [0%-2%] | 0.00 | 0.00 |
| approval, attentive reviewer | 0% | 100.0% [98%-100%] | 2.00 | 1.00 |
| approval, rubber-stamp reviewer | 100% | 0.0% [0%-2%] | 2.00 | 0.00 |
| capability token (argument-scoped) | 0% | 100.0% [98%-100%] | 0.00 | 1.00 |

### model obeys 30% of the time

| Policy | Exfiltration rate | Task success | Approval requests | Denied calls |
|---|---:|---:|---:|---:|
| none | 33% | 67.0% [60%-73%] | 0.00 | 0.00 |
| allowlist (tool names) | 33% | 67.0% [60%-73%] | 0.00 | 0.00 |
| approval, attentive reviewer | 0% | 100.0% [98%-100%] | 1.33 | 0.33 |
| approval, rubber-stamp reviewer | 33% | 67.0% [60%-73%] | 1.33 | 0.00 |
| capability token (argument-scoped) | 0% | 100.0% [98%-100%] | 0.00 | 0.33 |

**Measured findings**

- With no policy, and with a tool-name allowlist, the injected `send` to `attacker` executes in 100% and 100% of runs: the attack uses a tool the task legitimately needs.
- An attentive reviewer blocks all of them (0% exfiltration) at 2.0 approval requests per task; a reviewer who approves everything blocks none (100%).
- An argument-scoped capability token blocks all of them (0%) with zero human requests, and task success stays at 100%.

**Limitations of this experiment**

- This validates enforcement mechanisms, not attack resistance: the injection is a fixed marker and the model's susceptibility is a parameter.
- The capability policy works because the legitimate recipient set is known in advance. Open-ended recipients need a different control (data-flow tracking such as CaMeL, arXiv:2503.18813).
- Reviewer attentiveness is binary here. Real approval fatigue is gradual and grows with request volume.

## Tracing and replay

**Question.** What does it cost to record a run, and can a recorded run be replayed exactly?

**Conditions.** `{"replay": "ReplayModel + ReplayTools serve recorded results; request fingerprints must match", "tasks": 50}`

### 15-step tasks, 8% slips, 1 relocated key

| Loop | Events | Event log bytes | Spans | Span tree bytes | Replay identical |
|---|---:|---:|---:|---:|---:|
| react | 36.36 | 17,420 | 35.36 | 10,958 | 100% |
| plan_execute | 22.36 | 14,984 | 21.36 | 6,009 | 100% |
| verified_graph | 74.52 | 24,247 | 27.62 | 8,166 | 100% |

**Measured findings**

- A flat event log costs 17420 bytes per ReAct run (36 events); the derived span tree is 10958 bytes (35 spans).
- Replay from the recorded tape reproduced the complete event stream (payloads and timestamps) exactly in 100% of runs at worst, across all three loops, with zero backend calls.
- The trace is dominated by model-call payloads; plan-and-execute traces are smallest because they contain the fewest model calls (14984 bytes vs 17420).

**Limitations of this experiment**

- Events store full model responses but only a fingerprint of each request; reconstructing prompts requires replaying.
- Span timing uses the simulated clock.
